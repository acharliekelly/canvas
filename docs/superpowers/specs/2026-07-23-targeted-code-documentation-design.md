# Targeted Code Documentation Design

**Status:** Approved

**Date:** 2026-07-23

## Goal

Clarify CANVAS source code with targeted JavaDoc, TSDoc, Python docstrings, SQL and shell commentary, and inline comments that explain durable contracts and non-obvious invariants without narrating straightforward code.

## Scope

This is a documentation-only source pass. It may add or revise comments and documentation conventions, but it must not change runtime behavior, public APIs, schemas, dependencies, configuration, generated assets, or test assertions.

The pass targets code where correctness depends on lifecycle, concurrency, retry, security, accessibility, publication, persistence, or migration semantics. It does not require documentation on every public/exported symbol.

## Documentation standard

Add a targeted code-documentation convention to `AGENTS.md`:

- document module-facing contracts, invariants, side effects, idempotency and retry behavior, error guarantees, and security or accessibility constraints when they are not obvious from types and names;
- use JavaDoc for consequential Java types and methods, TSDoc for consequential exported TypeScript contracts, Python docstrings for worker contracts and behavior, and language-native comments for SQL and shell invariants;
- explain why a constraint exists and what callers may rely on;
- do not restate syntax, method names, ordinary control flow, getters, repository conventions, or obvious controller delegation;
- keep documentation updated in the same change when documented behavior changes;
- prefer refactoring over comments when code is confusing solely because it is poorly structured, while keeping refactoring out of this documentation-only pass.

## Java documentation

### Module boundaries

Enhance the Spring Modulith `package-info.java` files for `artwork`, `caption`, `description`, `identity`, `publication`, `shared`, and `storage` with package JavaDoc that describes ownership and the externally meaningful boundary. API subpackages need concise descriptions only when they clarify which DTOs/controllers form the exported contract.

### External ports

Add JavaDoc to:

- `ObjectStorage`: private-bucket abstraction, stream ownership, metadata lookup, idempotent deletion expectations, and distinction between original/generated qualified adapters;
- `CaptionClient`: one inference attempt behind a replaceable contract, error propagation, and draft-only result semantics;
- `AudioGenerator`: deterministic input identity versus generated bytes, approved-publication input requirement, and replacement compatibility metadata;
- `QrCodeGenerator`: exact public URI input and deterministic/versioned output expectations.

Document nested input/output records only where their fields encode identity, generator compatibility, byte ownership, or source provenance.

### Lifecycle-heavy services

Add class or method JavaDoc and focused inline comments to:

- `ArtworkService`: validate-before-store behavior and storage compensation if persistence fails;
- `DescriptionService`: immutable approved-revision history, in-place current-draft replacement, approved-revision preservation, artwork locking/version effects, and two-phase reorder used to preserve unique ordering constraints;
- `CaptionJobService` and `CaptionJobRunner`: single active job, explicit claim/run/finalize lifecycle, stale-work recovery, retry behavior, transaction boundaries, and retained successful results;
- `PublicationService`: approved-revision selection, immutable snapshot creation, current-only idempotency, A-to-B-to-A audit behavior, content-hash framing, exact asset association, and current-publication-only public authorization;
- `AssetService`: content-identity caching, transaction-scoped same-key serialization, repair eligibility, generator/config compatibility, object compensation, lock release after transaction completion, and limits of in-process locking.

Do not add JavaDoc to simple repositories, trivial controllers, enum constants whose names are self-explanatory, or ordinary entity accessors.

### DTO and record contracts

Document only records whose fields have non-obvious semantics:

- publication results, public asset/image streams, created/idempotent flag, artwork version, and versioned QR URL;
- generated binary metadata and approved-description identity;
- storage object metadata and stream/content ownership;
- caption job response fields if polling/lifecycle semantics are otherwise unclear.

Avoid duplicating validation annotations or obvious field names.

## TypeScript documentation

### API boundary

Add TSDoc to `apiFetch` explaining:

- same-origin session credentials;
- CSRF token acquisition and mutation-header behavior;
- JSON/problem response mapping;
- the shape of thrown API problems;
- the absence of automatic retry.

Add targeted TSDoc in `api/types.ts` for description revision/current-approved semantics, optimistic versions, caption job terminal/result fields, publication idempotency and versioned asset URLs, and public snapshot-only responses. Do not annotate every property.

### Complex interaction state

Use short inline comments or component/helper TSDoc in:

- `DescriptionEditor`: known generated-description IDs, artwork-version updates, focus restoration after approval dialog dismissal, dirty-draft approval prevention, and duplicate polling-result replacement;
- `CaptionRequestPanel`: polling ownership, terminal-state handling, and why a completed result may be delivered more than once safely;
- `PublishPanel`: current-approved revision selection, idempotent publication response, focus restoration, and QR/public-link state across rerenders;
- `SessionProvider` only if necessary to explain CSRF/session bootstrapping consumed by `apiFetch`.

Comments must describe accessibility or state invariants, not JSX structure or ordinary promise chains.

## Python documentation

Add module/class/function docstrings to the caption worker:

- describe `CaptionRequest` and `CaptionResponse` as the replaceable worker contract;
- document normalization validators only where blank-to-null or trimming behavior affects the contract;
- document health readiness and caption endpoint behavior;
- explicitly state that the deterministic placeholder validates `imageUrl` but does not fetch, decode, or analyze image content;
- state that returned text is draft material and the engine/version fields identify placeholder provenance.

Keep docstrings concise and compatible with normal Python introspection; do not repeat Pydantic type declarations.

## SQL and shell commentary

Add comments only to migrations and bootstrap logic with non-obvious safety behavior:

- `V3__description_revision_ownership.sql`: explain ownership backfill/constraint purpose if the sequence is not self-evident;
- `V5__retain_caption_job_results.sql`: explain why completed result references survive lifecycle changes;
- `V8__publication_asset_associations.sql`: explain removal of historical content uniqueness, conservative unique-match backfill, nullable ambiguous legacy associations, and `ON DELETE RESTRICT` provenance protection;
- `infrastructure/minio/create-bucket.sh`: explain root credentials being limited to server/bootstrap, scoped backend identity/policy creation, private buckets, and repeat-safe commands.

Do not comment basic table/column creation or shell syntax.

This documentation pass will not modify or stabilize that behavior. If it recurs, track it as a separate test/behavior task.

## Out of scope

- Runtime or test behavior changes.
- Refactoring complex code solely to make it easier to comment.
- Comprehensive documentation of every public method, DTO property, React prop, repository method, getter, or controller.
- New JavaDoc/TSDoc lint dependencies or repository-wide coverage gates.
- Generated API documentation publishing.
- Resolution of the observed flaky `PublishPanel` focus test.
